# Payments: design

HKCCS, HKIPZ, HKIPS, HKVPP and HKVPA as declarative segments; the pain.001 builder and pain.002 reader; transfer and instant transfer with the payee check (Verification of Payee, VoP); paused dialogs for a TAN in the same dialog. This design builds on [jobs-step-design.md](jobs-step-design.md) (`Step<T>`, `Resume<T>`, `Dialog::{submit_tan, poll, confirm_vop, cancel}`), [session-state-design.md](session-state-design.md) (`PausedDialog`, `freeze`/`thaw`), [version-negotiation-design.md](version-negotiation-design.md) (`Order`, `order_version`) and [return-codes-design.md](return-codes-design.md) (`Kind`, `Category`, `Notice::{Bank, Client}`).

**Sources.** "Messages" is `FinTS_3.0_Messages_Geschaeftsvorfaelle_2022-04-15`: C.10.2 (SEPA single orders), C.10.2.1 (HKCCS), C.10.2.9 (HKIPZ, HKIPS), D (data dictionary). "VoP" is `FinTS_3.0_Messages_Geschaeftsvorfaelle_VOP_1.02_2026_10_19`: C.10.7 (flow, migration), C.10.7.1.1 (HKVPP/HIVPP/HIVPPS), C.10.7.1.2 (HKVPA), D, E.8.1 (PIN/TAN flows; Abbildungen 3–5 are images in the PDF, pages 33–35). "PIN/TAN" is the 2020-07-10 security spec, B.4.2 (process variant 2). "RM" is the return codes 2026-02-03. "Anlage 3" is DFÜ-Abkommen Anlage 3 V26.11 (FV 09.04.2026, in force 15.11.2026; `spec/Anlage_3_Datenformate_V26.11.pdf`, [spec-sources.md](spec-sources.md)).

## 2. Public API

```rust
// jobs
pub async fn transfer(dialog: &mut Dialog, t: &Transfer) -> Result<Step<TransferReceipt>>;
pub async fn instant_status(dialog: &mut Dialog, from: &Account, receipt: &TransferReceipt)
    -> Result<Step<InstantStatus>>;                         // HKIPS or statement, section 3.7

pub struct Transfer {
    pub from: Account,                  // a UPD account with IBAN (and BIC)
    pub debtor_name: Option<String>,    // None: the UPD holder name (HIUPD), else InvalidTransfer
    pub payee_name: String,             // ≤ 70, SEPA charset
    pub payee_iban: String,             // checked: country, length 15..=34, mod 97
    pub payee_bic: Option<String>,      // 8 or 11; None: IBAN-only
    pub amount: Decimal,                // EUR, > 0, ≤ 999 999 999.99, at most two decimals
    pub purpose: String,                // unstructured remittance, ≤ 140, SEPA charset; may be empty
    pub end_to_end_id: Option<String>,  // ≤ 35, SEPA reference charset; None: generated by check()
    pub instant: Instant,
}
pub enum Instant { No, Prefer, Require }

pub struct TransferReceipt {
    pub sent_as: SentAs,                // Standard (HKCCS) | Instant (HKIPZ) | InstantConverted (3270)
    pub status: TransferStatus,         // Accepted | Executed (0020) | InstantPending { order_id: Option<String>, not_before: Option<Timestamp> }
    pub sent_on: Date,                  // the client's date when the order went out
    pub message_id: String,             // pain MsgId, generated
    pub end_to_end_id: String,          // as sent
    pub order_id: Option<String>,       // HIIPZ "Auftragsidentifikation"
    pub bank_reference: Option<String>, // 3070 P1
    pub payee_check: Option<VopResult>, // what the bank reported; None when no HKVPP was sent
}
```

- **Validation before contact** (`Transfer::check(upd_holder: Option<&str>) -> Result<CheckedTransfer, InvalidTransfer>`, also run by `transfer`; the checked value holds the parsed IBANs/BICs, the resolved debtor name and the end-to-end ID, so building the pain.001 cannot fail on transfer data): every rule above, plus `from` has an IBAN and the debtor name resolves (the given one, else the first non-empty UPD holder of the account). The first broken field is the error. The amount is EUR by type: `Account` carries no currency, so none is checked. Characters outside the SEPA set are **rejected**, never transliterated: the text set is the EPC basic Latin set (`a–z A–Z 0–9 / - ? : ( ) . , ' + space`) plus the characters Anlage 3 2.1 obliges banks to accept (`Ä Ö Ü ä ö ü ß & * $ %`). `formats::sepa::transliterate(&str) -> String` is public so a caller can offer the user a cleaned text. The error is `FinTSError::InvalidTransfer(InvalidTransfer { field, reason })` with `Category::InvalidInput` (caller's data; fix and retry; nothing was sent).
- **End-to-end ID.** A given `end_to_end_id` is checked as a SEPA reference. Without one, `check` generates one (`FC` + UTC `yyyyMMddHHmmss` + 8 random alphanumerics); the caller reads it from `CheckedTransfer::end_to_end_id()` and stores it before sending, because it matches a later booking to the order. The `EndToEndId` is never `NOTPROVIDED`; that value is sent only for a missing debtor BIC (section 5.4).
- **Pre-send checks** as every job: `order_version` for HKCCS/HKIPZ (and HKVPP when HIVPPS lists the order), `NoBpd`, `VersionMismatch`, no pain.001 version in common (`VersionMismatch` with code `pain.001` and both lists, `FormatLists { offered, implemented }`). The UPD's allowed-order list is not checked: a UPD `No` is reported in capabilities and the order is still sent, as for reads; the bank rejects before any challenge, so no TAN is spent.
- **Instant choice, before sending.** `No` → HKCCS. `Require` → HKIPZ, `VersionMismatch` when the bank does not offer it. `Prefer` → HKIPZ when offered and buildable, else HKCCS; with HKIPZ v2 and the BPD's "conversion allowed" = `J`, the conversion flag is set to `J` (the bank may then run it as a standard transfer, 3270 → `SentAs::InstantConverted`). Instant needs pain.001.001.09 (section 5.4). **No fallback after the bank answered:** an HKIPZ rejected with 9xxx (9210 "too large for instant", 9255 limit) fails the job; the caller may retry with `Instant::No`, which runs a new payee check and a new TAN. Sending a second payment automatically after a rejection is not safe to decide for the user.
- **`Done`** carries the `TransferReceipt` and, as every job, every notice of every message (VoP explanation texts are in the `VopResult`, not lost). `Accepted` is 0010 or 3076 without 0020; `Executed` is 0020. `InstantPending` is 3045 in the HKIPZ answer; `order_id` is `None` when the bank sent no HIIPZ, `not_before` is the arrival plus HIIPSS "Mindestwartezeit" (`None` without HIIPSS). `sent_on` is the client's local date (or the one pinned with `BankClient::with_now`) when the order went out.

`Step<T>` (see [jobs-step-design.md](jobs-step-design.md)) has two variants for transfers:

```rust
pub enum Step<T> {
    Done(Completed<T>),
    NeedTan(TanChallenge, Resume<T>),
    NeedVopConfirmation(VopConfirmation, Resume<T>),   // answer: dialog.confirm_vop(resume) or dialog.cancel(resume)
    VopPending(VopWait, Resume<T>),                    // answer: dialog.poll(resume) at or after not_before
}
pub struct VopConfirmation {
    pub result: VopResult,
    pub explanation: Option<String>,    // HIVPP "Aufklärungstext …": must be shown (VoP C.10.7.1.1)
    pub explanation_markup: bool,       // HIVPPS "Aufklärungstext strukturiert": the text may hold <br> <p> <b> <i> <u> <ul> <ol> <li> <a href>
    pub valid_until: Option<jiff::civil::DateTime>, // HIVPP "VOP-ID gültig bis", bank local time
}
pub struct VopResult { pub payees: Vec<PayeeResult>, pub notes: Vec<String> }   // one entry for a single transfer; empty on 3095
pub struct PayeeResult {
    pub iban: String, pub requested_name: String,
    pub outcome: PayeeOutcome,
}
pub enum PayeeOutcome {
    Match,                                        // RCVC
    CloseMatch { registered_name: Option<String> }, // RVMC + "Abweichender Empfängername"
    NoMatch,                                      // RVNM
    NotApplicable { reason: Option<String> },     // RVNA + "Grund RVNA"
    Pending,                                      // PDNG (only inside an unfinished result)
    OtherId { id_name: String, outcome: Box<PayeeOutcome> }, // "Anderes Identifikationsmerkmal" (e.g. LEI)
}
pub struct VopWait { pub not_before: Option<jiff::Timestamp>, pub polls_done: u32 }  // polls_done: HKVPP polls sent, message 1 not counted
```

`Dialog::confirm_vop(resume) -> Result<Step<T>>` sends the execution order (section 3.3) and returns `NeedTan` (or `Done` on 3076). When every payee matched (the user was asked only because of 3090 or an explanation text) and the TAN of message 1 is still live, it returns `NeedTan` for that challenge without sending. On a job that is not waiting for a confirmation it returns `FinTSError::Dialog` and leaves the job paused, as `poll` does on a typed challenge.

`Dialog::cancel(resume) -> Result<Cancelled>` sends nothing. `Cancelled::NothingSent` at a payee check: the bank executes only after the execution order (VoP C.10.7: the customer consents "mit der Einreichung des Ausführungsauftrags (HKVPA)"), the stored order is discarded and its VoP-ID expires (VoP C.10.7.1.1: a corrected name means a new order). On `VopPending` it is also `NothingSent`: the bank has sent no VOP-ID (VoP C.10.7.1.1 point 6: only after the final result) and no challenge, so nothing can release the order. `Cancelled::OrderSubmitted { end_to_end_id, message_id }` on a `NeedTan`, and on a `NeedVopConfirmation` that holds a live decoupled challenge of message 1 which the bank releases without HKVPA (3091): the order is at the bank and a late approval in the app may execute it. The caller checks the account before sending it again.

`Dialog::poll` on a `VopPending` job sends the next HKVPP (section 3.4) instead of an HKTAN status request; the library never sleeps.

The `NeedTan` of a transfer carries the payee check result: `TanChallenge::payee_check: Option<VopResult>`, so a caller shows "payee confirmed" next to the TAN prompt or app approval (VoP E.8.1 point 3: with decoupled methods the positive result should be shown parallel to the approval request).

## 3. Flow

All messages are in the job's dialog. "Order" is the HKCCS or HKIPZ segment with the pain.001 bytes. HKTAN references the order segment, never HKVPP. Rules from VoP E.8.1 points 1–6 and Abbildungen 3–5; the flow is **steered by return codes, not by the result codes in HIVPP** (VoP E.8.1, note after point 5).

### 3.1 Message 1: check and order

`HKVPP + order + HKTAN:4` (Abbildung 3/4: HKVPP first). Segment numbers 3, 4, 5. HKVPP field 2 lists the pain.002 descriptors from HIVPPS that the client reads: those naming `pain.002.001.10`, all of them when none does (the bank's string as announced). The polling ID, maximum entries and touchdown fields are empty; both VoP banks announce "Eingabe Anzahl Einträge erlaubt" = `N`.

HKTAN for a payment order: always process 4 when the security function is two-step. `order_tan` keeps the profile override first; otherwise a payment order counts as TAN-required regardless of HIPINS (PIN/TAN B.4.2: transfers are the example of a TAN-required order; all three banks list `J`). This also means the 9075 "resend with HKTAN" retry can never resend a payment.

### 3.2 Answer to message 1

Checked in this order:

| Answer | Meaning | Step |
|---|---|---|
| class 9 on HKVPP or the order | rejected (9076, 9210, 9250, 9230, 9390, …) | `Err` (dialog stays `Open`) |
| 3093, or HIVPP without VOP-ID and no challenge (3040 with a touchdown point and a polling ID only when the bank sends them) | result not complete | `VopPending` (3.4) |
| 3076 and the order's 0010/0020, no HITAN | the bank waived VoP and SCA (E.8.1 point 2; 3091 with it) | `Done` |
| HITAN with a challenge, no 3945 | the TAN is live | clean match → `NeedTan`; otherwise `NeedVopConfirmation`. After `confirm_vop`: when every payee matched (only 3090 or a text asked the user), `NeedTan` for the **same** challenge without sending; when a payee did not match, the execution order of 3.3 (VoP E.8.1 point 4: on a name deviation HKVPA, HKTAN and the order always go together) |
| 3945 on HKTAN (no valid challenge) | the bank wants HKVPA with a fresh HKTAN | clean match → send message 3.3 at once; otherwise `NeedVopConfirmation` |

An answer with neither a challenge nor 0010/0020/3076 on a segment fits no case and is `PaymentOutcomeUnknown` (3.5).

**Clean match:** every `PayeeResult` is `Match`, no 3090 in the answer, and no explanation text. An empty result counts as a match: 3095 and a final HIVPP without a result (DEG or pain.002) are a notice, not a deviation, and give `payee_check: Some(VopResult::empty())`; so does a final answer with 3091 and no result. Anything else (close match, no match, not applicable, 3090 next to a match, an explanation text) asks the user. The spec lets the bank steer the flow by codes, so the client asks whenever the bank signals anything; a bank that always answers 3945 (E.8.1 note) still adds no confirmation step on a clean match.

**HKVPA with the TAN.** When HITAN came without 3945 and without 3091, the bank expects HKVPA with the TAN answer (Abbildung 3, red steps): `submit_tan` sends `HKVPA + HKTAN:2`; for decoupled methods the first `poll` sends `HKVPA + HKTAN:S`, later polls `HKTAN:S` alone. With 3091 no HKVPA is sent. The spec does not say whether a decoupled bank also wants HKVPA on every later poll; the live run at DKB (decoupled) took the first-poll-only form ([banks.md](banks.md)). A bank that deviates gets a profile field, not a branch.

### 3.3 Execution order (after confirmation, or after 3945 on a clean match)

`HKVPA(VOP-ID) + order + HKTAN:4` (Abbildung 4). The order carries **the same pain.001 bytes** as in message 1 (VoP C.10.7.1.2: "Die ursprüngliche pain-Nachricht muss dabei erneut eingereicht werden"; the bank answers 9010 "Auftrag weicht vom Ursprungsauftrag ab" otherwise). The answer is an ordinary order answer: HITAN → `NeedTan`; 3076 + 0010/0020 → `Done`; 9xxx → `Err` (9010 "VOP-ID unknown/differs", 9210 "already executed").

### 3.4 Polling the payee check

When HIVPP has no VOP-ID, the job pauses with `VopPending { not_before }`: arrival plus HIVPP "Wartezeit vor nächster Abfrage" (seconds; `None` when absent, the caller then uses its own default as for decoupled TANs). `poll` sends **HKVPP alone** with the touchdown point (3040 P1) of the last answer and, only next to it, the polling ID when the bank sent one (VoP C.10.7.1.1, HKVPP "Belegungsrichtlinien": field 3 only with a touchdown point); no order, no HKTAN. A pending answer without a polling ID (3093 alone) is still pending. Each answer is again classified by 3.2. pain.002 parts: with delivery `S` the parts are merged by `OrgnlEndToEndId`; with `V` the last part is the result; another delivery code is read like `V`, with a warning (VoP D, "Art der Lieferung"). After the final HIVPP the message-1 HKTAN is void in practice (E.8.1 note: 3945 "insbesondere für das Polling"), so the job continues with 3.3: directly on a clean match, else via `NeedVopConfirmation`. There is no poll limit in the BPD; 9250 ends the job (`Temporary`).

### 3.5 TAN

After `NeedTan` the existing `submit_tan` / `poll` apply (typed: HKTAN process 2 with the TAN in HNSHA; decoupled: process S, 3956 counted against HITANS max polls). The answer that confirms the TAN is the order's answer (PIN/TAN B.4.2: "Alle Rückmeldungen in der letzten Antwort beziehen sich auf den Auftrag selbst"): any answer without a class 9 error ends the job with the receipt, and HIIPZ is read when present. **Never resent:** a payment has no data segment, so the "confirmation without data segment → send the order again" rule of the read jobs does not apply; `JobInput::order()` is `None` for a transfer.

**Outcome unknown.** After a message that carried the order or its TAN (3.1, 3.3, the TAN answer, the decoupled status requests), every error that is not a class 9 rejection ends in `FinTSError::PaymentOutcomeUnknown { end_to_end_id, message_id }` (`Category::OutcomeUnknown`, as 9000): a transport error, an unreadable HITAN, HIVPP or pain.002, an answer that fits no case. So does `poll` past the HITANS `max_polls` on a transfer's decoupled TAN (reported without sending), and so does a dropped future: the dialog ends, the in-flight marker keeps the payment's IDs, and the next call on the dialog (any job, `submit_tan`, `poll`, `cancel`, `freeze`, `end`) returns `PaymentOutcomeUnknown` once, then `DialogEnded`. The caller must check the account (by `end_to_end_id`, `message_id`) before trying again. Job futures are not cancel-safe (see [jobs-step-design.md](jobs-step-design.md)). On HKVPP-only polls the outcome is known (nothing was ordered) and the error is the plain one.

### 3.6 Banks without HIVPPS, and orders HIVPPS does not list

No HIVPPS, or HIVPPS does not list the order's code: message 1 is `order + HKTAN:4`, no payee check, `payee_check: None`. A 3092 ("VoP required from P1") becomes a typed notice; a 9076 is the `VopRequired` error (`Unsupported`). Consorsbank takes this path.

### 3.7 Instant status (HKIPS)

Messages C.10.2.9.2 makes HKIPS mandatory for a client that sends HKIPZ. On 3045 in the HKIPZ answer the job ends with `TransferStatus::InstantPending { order_id, not_before }`, and the caller asks later with `jobs::instant_status(dialog, from, &receipt)` → `InstantStatus { status: Option<SepaOrderStatus>, again_after: Option<Timestamp>, source: StatusSource }` (3045 again → `status: None` and `again_after`; `source` is `StatusRequest`). The transfer job does not wait for it: the payment is already submitted, and a dropped pending job must never lose the receipt. HKIPS uses the normal `order_tan` rule: PIN/TAN B.3 leaves the TAN to the bank's HIPINS entry, and Messages C.10.2.9.2 sets none for HKIPS. DKB and comdirect list HKIPS `N`; a bank that lists it `J` makes the step `NeedTan`.

- `SepaOrderStatus` is the HIIPS "Status SEPA-Auftrag" list (codes 1 to 9: `Scheduled`, `RejectedByFirstCollector`, `InProcess`, `Processed`, `ReturnInitiated`, `Failed`, `Executed`, `RejectedByPayerPsp`, `RejectedByPayeePsp`) with `Other(String)` for any other code. `Done` with `status: None` and `again_after: None` means the bank answered without a status and without 3045.
- **Without HKIPS.** A bank can offer HKIPZ without HIIPSS (Consorsbank's BPD), and a receipt can lack the order ID (no HIIPZ). Then `instant_status` reads the account's statement from `receipt.sent_on` to today (HKCAZ or HKKAZ, chosen as for `transactions`) and looks for a debit with the receipt's end-to-end ID: booked → `Executed`, pending → `InProcess`, not found → `status: None`; `again_after` is `None` and `source` is `StatusSource::Statement`. It is the client's reading, not the bank's word, and a bank that sends no pending bookings shows the payment only once booked. The job is the transactions job with the ID to look for (`JobInput::Transactions::find_payment`); it pauses for a TAN like any read and resumes as `AnyResume::InstantStatus`. With HKIPS offered but no version or format in common, the fallback is taken as well; without a BPD, `NoBpd`.
- HKIPS carries one pain.001 descriptor chosen like the one for HKIPZ (HIIPSS formats, else HISPAS; 001.001.09 first); none in common is the `pain.001` `VersionMismatch` before anything is sent. The spec names the HIIPSS schema (pain.001 "Kunde-Bank") for the "SEPA pain message" of the answer; the test bank sends none back.
- With a TAN, 3045 and HIIPS come with the TAN answer. That answer ends the job when it carries HIIPS or 3045 (3045 with or without HIIPS is `status: None`); with neither, HKIPS is sent again, as for any read whose TAN answer carries no data. The job never repeats HKIPS after a 3045: Messages C.10.2.9.2 lets the client ask once more, and that is the caller's next `instant_status` call.
- Capabilities: `JobKind::{Transfer, InstantTransfer, InstantStatus}`, and `AccountCapabilities::payee_check: Option<VopSupport { required_for: Vec<SegmentType> }>` from HIVPPS (`None` without it).

### 3.8 Paused dialogs

The TAN must be given in the dialog that received the order (the task reference lives in that dialog; PIN/TAN B.4.2 allows cross-dialog only through the task reference, which the banks need not support). `freeze`/`thaw` (session-state design) keeps the dialog, and the payment job is part of it:

- `JobInput::Transfer(Box<PaymentJob>)`: the debtor account, the order kind (HKCCS, or HKIPZ with its version and conversion flag), the pain.001 descriptor, the pain.001 as a UTF-8 string, `message_id`, `end_to_end_id`, the normalised payee IBAN and name, `hkvpa_with_tan`, and `vop: Option<VopState>` (HKVPP descriptors, delivery, VOP-ID, valid until, polling ID, touchdown, polls done, the pain.002 parts as bytes, result, explanation, the 3090 and 3091 flags, and the live challenge of message 1 while the user decides). The pain.001 is stored verbatim because 3.3 must resend it byte for byte (it contains `CreDtTm` and the generated IDs). There is no order hash in process variant 2 (hash procedure 0); the bank identifies the order by task reference and VoP-ID.
- `PendingJob` waits on `Wait::{Tan(TanChallenge), VopConfirmation(VopConfirmation), VopPoll(VopWait)}`; `Resume<T>` holds a `Ticket::{Task(TaskReference), Local(u64)}` (random nonce for the two VoP waits, checked like the task reference).
- `AnyResume::Transfer(Resume<TransferReceipt>)`, `AnyResume::InstantStatus(..)`; `PausedDialog::challenge()` is TAN-only, `PausedDialog::vop()` returns the confirmation, `PendingJob::vop_wait()` the wait.
- `PausedDialog` is sensitive (session-state §2): it holds payee names, IBANs and amounts.

## 5. `formats`

### 5.1 pain.001 builder (`src/formats/pain001.rs`)

- **Versions:** pain.001.001.09 and pain.001.003.03 (section 1). The descriptor is chosen per order: HIIPZS formats for HKIPZ (HISPAS when HIIPZS lists none), HISPAS formats for HKCCS; prefer 001.001.09, then 001.003.03; the announced string is sent exactly as listed (comdirect lists the URN with and without `.xsd`: the first entry that names the version is used). The XML namespace is the URN without `.xsd`.
- **Shape** (Messages C.10.2: one `PmtInf`, one `CdtTrfTxInf`; Anlage 3 for elements): `GrpHdr` (`MsgId`, `CreDtTm` local ISO time, `NbOfTxs` 1, `CtrlSum`, `InitgPty/Nm` = debtor name), `PmtInf` (`PmtInfId`, `PmtMtd` TRF, no `BtchBookg` (C.10.2: do not set it), `NbOfTxs`, `CtrlSum`, `PmtTpInf/SvcLvl/Cd` SEPA, for HKIPZ also `LclInstrm/Cd` INST, `ReqdExctnDt` **1999-01-01** (C.10.2.1; in .09 inside `<Dt>`), `Dbtr/Nm`, `DbtrAcct/Id/IBAN`, `DbtrAgt` (`BICFI` in .09, `BIC` in 003.03; `Othr/Id` NOTPROVIDED when the account has no BIC), `ChrgBr` SLEV), `CdtTrfTxInf` (`PmtId/EndToEndId`, `Amt/InstdAmt Ccy="EUR"` two decimals, `CdtrAgt` only with a BIC, `Cdtr/Nm`, `CdtrAcct/Id/IBAN`, `RmtInf/Ustrd` when the purpose is not empty).
- **IDs:** `MsgId` and `PmtInfId` = `FC` + UTC `yyyyMMddHHmmss` + 8 random alphanumerics (24 characters, SEPA reference set). `EndToEndId` from the caller, else generated in `Transfer::check` with the same scheme (section 2).
- **Escaping:** written with `quick-xml`, so `&`, `<`, `'` are escaped by the writer; text is UTF-8 and declared so.
- **Tests:** golden XML per version (standard and without BICs for each, instant for .09; `tests/fixtures/pain/`), a validation table, and namespace/descriptor choice per bank BPD (section 1). XSD validation is not run in CI (no schema dependency). The golden files validate with `xmllint --schema` against `pain.001.001.09_GBIC_5.xsd` and `pain.001.003.03.xsd` (`spec/pain/`, checked by hand 2026-11-17). Regenerate with `UPDATE_GOLDEN=1 cargo test -p fints-client --lib pain001` and validate again.

### 5.2 IBAN, BIC, charset (`src/formats/sepa.rs`)

`Iban::parse` (country letters, 15..=34 alphanumerics, mod 97 = 1, spaces removed, upper-cased) and `Bic::parse` (8 or 11, `AAAA BB CC (DDD)`) are inherent methods on `types::Iban`/`Bic` and fail with `sepa::Invalid`, which implements `Error`. `is_sepa_text`, `is_sepa_reference` (no leading/trailing `/`, no `//`) and `transliterate` are public; the rest is crate-private. The account types keep their own constructors.

### 5.3 pain.002 reader (`src/formats/pain002.rs`)

Both VoP banks announce pain.002.001.10 in HIVPPS, and HIVPP may carry the result as pain.002 even for one transaction (VoP C.10.7.1.1: the single-transaction DEG is the bank's choice, and banks that use it may still send pain.002). The reader covers only the VoP status report: `OrgnlGrpInfAndSts` (`OrgnlMsgId`, `NbOfTxsPerSts`), `TxInfAndSts` (`OrgnlEndToEndId`, `TxSts` = RCVC/RVMC/RVNM/RVNA/PDNG, the registered name for RVMC and the reason for RVNA at the elements Anlage 3 names, the requested `Cdtr/Nm` and `CdtrAcct` from `OrgnlTxRef`), and merging stepwise parts. It is crate-private, XML only: `read(parts, message_id, sent) -> StatusReport` with status codes; the VoP types and the HIVPP DEG live in `jobs::transfer::vop`. It produces the same `VopResult` as the HIVPP single-transaction DEG. A pain.002 that does not parse fails the job with `FinTSError::Pain002` and the raw bytes are in the trace, never a guessed match.

Reading rules:

- The last status a transaction got wins across parts (complete and stepwise delivery alike).
- A sent transaction that is not listed (Anlage 3 2.2.6.6 requires only the non-RCVC ones), or listed `PDNG` and not listed again in a later part, is a match when the last part confirms matches (a `PmtInfSts` or `GrpSts` of `RCVC`, or an `RCVC` count covering them). Otherwise, for an order of one transaction, its status is the last part's `PmtInfSts`, else `GrpSts`, else the one status the counts name (`RVCM` names none). Anything else is `FinTSError::Pain002`.
- Also `Pain002`: another `OrgnlMsgId`, an unknown `TxSts`, unreadable XML.
- RVMC: the registered name is the first `AddtlInf` joined with the second (continuation past 105 characters). RVNA: the `AddtlInf` text, else the reason code (`AB11`, `AG03`).
- Group `StsRsnInf/AddtlInf` lines (each starting with its status code) go to `VopResult::notes`. Listed transactions that answer none of the sent ones are kept at the end of `payees`.
- HIVPP DEG (`jobs::transfer::vop::read_result`): an "Anderes Identifikationsmerkmal" wraps the outcome in `OtherId`. The DEG does not repeat the requested name, so the caller passes it.

### 5.4 Format rules

Anlage 3 V26.11 sections: 2.1 (character set, names ≤ 70, references without leading/trailing `/` or `//`), 2.2.1 (pain.001.001.09), 2.2.4.1 (SCT Inst: `LclInstrm/Cd` `INST`, on `PmtInf` level), 2.2.6 (VoP status report pain.002.001.10: 2.2.6.4–2.2.6.7), 2.3.1.1 (IBAN, BIC, `Max35Text` reference pattern), 2.3.3 (amount 0.01–999 999 999.99). pain.001.003.03 is not in V26.11; its shape comes from the DK schema in the Anlage 3 V2.9 archive.

- **Character set.** Anlage 3 2.1 obliges banks to accept `* $ %` as well as `Ä Ö Ü ä ö ü ß &`; the text set (names, purpose) includes all of them. References (`EndToEndId`, `MsgId`, `PmtInfId`) use the narrower basic set of the `Max35Text` pattern. `transliterate` keeps every character of the text set, strips accents and spells out ligatures, maps other whitespace to a space, typographic quotes and dashes to `'` and `-`, and anything else to `.`.
- **Instant needs pain.001.001.09.** pain.001.003.03 has no `LclInstrm`, so it cannot carry `INST` (Anlage 3 2.2.4.1). `choose_descriptor(offered, instant)` skips 003.03 for HKIPZ: a bank that offers only 003.03 for HKIPZ gets `VersionMismatch` (`Require`) or HKCCS (`Prefer`).
- **Debtor BIC.** `Account` always has a BIC string; one that `Bic::parse` rejects is sent as `Othr/Id` `NOTPROVIDED` rather than failing the transfer (bank data, not the caller's).
- **Debtor name.** `check` resolves `None` against the UPD holder (`InvalidReason::NoName` when neither exists); `build` takes the resolved name.
- **Time and IDs.** `CreDtTm` is the machine's local time. `transfer` generates the pain IDs and `CreDtTm` and passes them to `PaymentJob::prepare`, so `prepare` is deterministic in tests. The HKIPZ version is chosen before the pain.001 is built and kept with the job. The receipt and the paused job carry the normalised payee IBAN.
- **Crate-private API.** `choose_descriptor(offered, instant)`, `PainIds::generate(now, rng)`, `build(&Pain001Input, descriptor, ids, created) -> Pain001` (infallible). `rand` is not in the public API; only the SEPA text helpers, the IBAN/BIC parsers and the VoP result types are public.

## 6. Codec

Each segment is a `#[derive(Segment)]` in `src/codec/defs/` with a wire-string test ([codec.md](codec.md)); parameter segments join the typed BPD (bpd-upd-design §2) with accessors (`Bpd::vop()`, `Bpd::sepa_formats(order)`, `Bpd::instant()`); `Order` has `Transfer` (HKCCS), `InstantTransfer` (HKIPZ), `VopCheck` (HKVPP), `VopExecute` (HKVPA), `InstantStatus` (HKIPS); `JobDetail::Vop` holds HIVPPS. The protocol layer has `Segment::{CreditTransfer, InstantTransfer, VopCheck, VopExecute}`, `send_payment` (leading segments, the order, HKTAN), `send_vop_poll`, and `send_tan`/`send_tan_status` with leading segments (HKVPA next to HKTAN:2/S).

## 7. Test bank

`testbank` answers payments from `BankModel::payments: Option<PaymentsModel>` (`testbank/src/model.rs`); the engine side is `testbank/src/engine/payments.rs`, a child of `engine`, which owns the dialog and TAN state. The three profiles in `profiles.rs` carry the payment facts of section 1 and [banks.md](banks.md); tests are `testbank/tests/payments.rs` and `tests/payments_test.rs`.

- **BPD.** `PaymentsModel { hkccs, hkccs_formats, hkipz_versions, hkipz_formats, hkipz_purpose_codes, hkipz_conversion_allowed, hkips: Option<InstantStatusModel { min_wait, formats }>, instant_limit, instant_limit_answer: LimitAnswer, instant_status_after, payees, not_applicable, vop: Option<VopModel>, tan_codes_on_order }`. `VopModel { max_transactions, structured_text, delivery: Stepwise | Complete, psr_formats, required_orders, result_as: Pain002 | SingleDeg, pending_polls, wait_secs, hkvpa_on_match: OnMatch::{Skip3091, Require, Always3945}, explanation, list_matches, polling_id, empty_result, challenge_on_deviation, deviation_on_match, block_status_only, message_notice, vpa_answer, order_answer_after_vpa }`. HICCSS 1 / HIIPZS 1, 2 / HIIPSS 1 / HIVPPS 1 / HIVPAS 1 / HISPAS come from it; HIPINS lists HKCCS and HKIPZ `J` (`enable_payments`) and whatever else the profile puts into `jobs`. Payment orders ignore `JobSpec::server_tan` except `Exempt`/`RequiredExempt`, which waive the TAN (3076 and execution at once). With `tan_codes_on_order` the TAN codes (`0030`, `3955`) of a challenge come on the order segment instead of HKTAN (Consorsbank).
- **Payees.** A synthetic registry `IBAN → registered name` in the model. Exact (case-insensitive) → RCVC; registered name differs only in case-folded punctuation, word order or one missing given name → RVMC with the registered name; otherwise RVNM; IBANs in `not_applicable` → RVNA with a reason. Synthetic IBANs and names only (AGENTS.md "Fixtures"). All three profiles share a registry (`Anna Beispiel`, `Berta Maria Muster`, one RVNA IBAN).
- **Message 1** (`HKVPP + order + HKTAN:4`, strict order and shape, HKTAN must name the order): answers on HKVPP (segment 3): `0025` [+ `3091` with `Skip3091`] on a match, `3090` otherwise; HKTAN gets the challenge (`0030`/`3955`), or `3945` after a deviation and with `Always3945`. `Require` expects HKVPA + HKTAN with the TAN (first message only; later decoupled polls go alone); a TAN message without it, or with it when the bank waived it, is a violation; an HKVPA with a wrong VOP-ID is `9010` on HKVPA and keeps waiting.
- **Polling.** `pending_polls = n`: the first n HKVPP answers (message 1, then each HKVPP alone) are pending: `3093` + `3040` with touchdown `VP-<k>`, HIVPP with polling ID (`POLL<nnnn>`; none with `polling_id: false`), wait, no VOP-ID; the HKTAN of message 1 stays unanswered. A poll must carry the last touchdown point and, next to it, the polling ID when one was sent (else violation). The final answer carries `3094` and `0025` or `3090`, the VOP-ID (`VOPID<nnnn>`) and the result; the client then sends `HKVPA + order + HKTAN:4`, never a TAN from message 1. Switches: `empty_result` (final answer `3095`, no result), `challenge_on_deviation` (a challenge in message 1 also after a deviation; the client must still send the execution order), `deviation_on_match` (`3090` next to a match), `block_status_only` (pain.002 with `PmtInfSts` only, no counts, no `TxInfAndSts`), `list_matches: false` (a matching transaction is left out of `TxInfAndSts`, so a match is read from `NbOfTxsPerSts` alone). With `Stepwise` each pending answer holds a partial result (pain.002 with `PDNG`, or the DEG with `PDNG`); with `Complete` only the last answer holds one.
- **Execution order.** `HKVPA(VOP-ID) + order + HKTAN:4`: unknown VOP-ID `9010` ("VOP-ID unbekannt oder abgelaufen") on HKVPA; an executed one `9210`; other pain bytes or order code `9010` ("Auftrag weicht vom Ursprungsauftrag ab") on the order. Checks on every order: descriptor and version in the BPD (else violation), account allowed (`9210`/model code), `ReqdExctnDt` 1999-01-01 (`9150`), INST in an HKIPZ pain (an HKIPZ without it stays `9150`), `MsgId` not executed before (`9390`). A required check without HKVPP is `9076`; no HKTAN `9075`. `vpa_answer` and `order_answer_after_vpa` carry the codes a bank puts on HKVPA and on the order after it.
- **Instant.** Above `instant_limit`: `9255` with a link parameter or `9210`; HKIPZ 2 with the conversion flag `J` and `hkipz_conversion_allowed` is executed as a standard transfer and answers `3270` (with the TAN answer). `instant_status_after = n > 0`: the TAN answer carries `3045` and HIIPZ status 3; HKIPS is answered `3045` until the n-th query, then HIIPS status 7. HIIPZ order IDs are `INST<nnnn>`. The client never builds HKIPZ with pain.001.003.03 (5.4).
- **pain.002 (Anlage 3 2.2.6.6 and 2.2.6.7).** `OrgnlGrpInfAndSts` (`OrgnlMsgId`, `OrgnlMsgNmId`, `NbOfTxsPerSts` with the status), `OrgnlPmtInfAndSts/TxInfAndSts` (`OrgnlEndToEndId`, `TxSts`, `StsRsnInf`, `OrgnlTxRef/Cdtr/Pty/Nm` and `CdtrAcct/Id/IBAN`). The registered name of RVMC is the first `StsRsnInf/AddtlInf`; RVNA is `StsRsnInf/Rsn/Cd` AG03 with the reason text in `AddtlInf` (the AB11 time-out variant is not modelled). The report echoes the received pain.001 namespace in `OrgnlMsgNmId`. By default the bank lists the transaction also on a match; Anlage 3 requires only the non-RCVC ones (`list_matches`).
- **Inspection.** The bank records submitted payments (`BankHandle::payments()`), so tests assert exactly one execution.
- **Profiles.** `dkb()`: HKCCS .03/.09, HKIPZ 1 and 2 (.09, conversion `N`), HIIPSS 5, VoP `V`, unstructured, pain.002 URN, 14 required orders, decoupled TAN. `comdirect()`: HKCCS .003.03 (also `.xsd`), HKIPZ 1 with the purpose codes and four formats, HIIPSS 99 with two, VoP `S`, structured, `sepade.pain.002.001.10.xsd`, 9 required orders. `consorsbank()`: the six pain.001 strings for HKCCS and HKIPZ 1, no HIIPSS, no VoP, `tan_codes_on_order`. DKB and comdirect use `OnMatch::Require` and pain.002 (clean match seen live at DKB 2026-11-20: `3090` + `0025`, `3945`, then HKVPA; [banks/dkb.md](banks/dkb.md)).

`tests/payments_test.rs` covers: match with 3091 (typed and decoupled), match without 3091 (HKVPA + HKTAN:2 / first S), match with 3945 (no confirmation step, HKVPA message), close match / no match / not applicable → `NeedVopConfirmation` → confirm → TAN → `Done`; cancel at confirmation (nothing executed); polling with `V` and `S` (parts merged, `not_before` from the wait); bank without HIVPPS; instant: require not offered (nothing sent), prefer → HKCCS, limit rejection (no fallback), conversion, 3045 + `instant_status`, HKIPS with a TAN (3045 in the TAN answer, then HIIPS after a freeze and thaw), no HKIPS: the payment found in the statement (`Executed`) and not found (`None`); freeze/thaw at each wait (confirmation, VoP poll, TAN) through JSON into a new client; a cut wire after message 1 and after the TAN answer → `PaymentOutcomeUnknown` and exactly zero or one execution at the bank; validation table sends nothing; the profile switches of the polling bullet.

## 8. Live test

A human runs it. `examples/transfer.rs` (feature `trace`), run through `scripts/try-bank.sh <BLZ> --transfer`: credentials by hidden prompt (product ID from `.env`), never on the command line; payee name, IBAN, BIC (optional), amount (default `1.00`), purpose and instant choice by prompt; shows the VoP result and explanation and asks `confirm? [y/N]`; TAN by hidden prompt or "approve in the app, then press Enter" (honours `not_before`); prints the receipt; writes a masked trace to `testbank/fixtures/replay/local/<bank>-<BLZ>.transfer.trace.json` (git-ignored). Masking covers the pain.001 inside HKCCS/HKIPZ/HKVPP and the names, IBANs and pain.002 in HIVPP (`src/mask/`). The payee is your own account at another bank; the script refuses amounts above 1.00 unless `FINTS_ALLOW_AMOUNT` is set. From the repository root:

```
scripts/try-bank.sh <BLZ> --transfer   # characters 5 to 12 of the IBAN you send from
```

Run once with the exact name of the payee (expect no confirmation step where the bank checks payees) and once with a deliberately wrong name (expect `NeedVopConfirmation`; confirm to send 1 EUR, or cancel). Results go into [banks.md](banks.md).
